# x402 premium data

Ward buys on-chain intelligence from pay-per-call APIs on Base. A request is
priced in the HTTP `402` response, paid in USDC over EIP-3009, and settled through
the Coinbase facilitator — the agent spender pulls the funds within the on-chain
Spend Permission, and the whole spend still passes the memory gate first.

## The catalog

`memory/catalog/x402-catalog.json` — a static list. Discovery is a keyword score
over `name` / `description` / `tags` (`searchCatalog`), not a vector search.

```jsonc
{
  "id": "token-risk",
  "name": "Token Risk Score",
  "description": "Rug-pull and honeypot risk assessment for an ERC-20 on Base…",
  "url": "https://x402.elizaos.ai/api/analytics/analyze_token",
  "method": "POST", // GET or POST/PUT/PATCH (case-insensitive)
  "body_template": { "token_address": "{subject}", "depth": "full" },
  "cost_usd": 0.05, // shown at confirmation
  "tags": ["risk", "rug", "scam", "safety", "honeypot"],
}
```

- **`method`** — normalised to upper-case on load. GET/HEAD send no body.
- **`body_template`** — sent as an `application/json` body on POST/PUT/PATCH.
- **`{subject}` / `{token}`** — in `url` (any method) and in every string value of
  `body_template`, replaced with the token the user asked about (a ticker or a
  `0x` address). `resolveX402Call(endpoint, subject)` does the fill and returns the
  concrete `{ url, method, body? }`.
- If an endpoint needs a subject and the message names none, `confirm` replies
  **"Which token? Give me a ticker or a 0x address."** and stops — no payment.
- **`cost_usd`** is the _expected_ price. The real price comes from the `402`
  response and is hard-capped at `cost_usd × 1.5` (`maxUsd`, passed to
  `wrapFetchWithPayment`). Over that, the payment throws and nothing is charged
  beyond gas.

The four bundled endpoints were sourced from the CDP x402 Bazaar (via x402scan).
**Verify each one's method + body shape against its live `402` before a
real-money demo** — their contracts can change, and several Bazaar endpoints are
POST with required body fields.

Point `WARD_X402_CATALOG` at another file to override.

## When the agent calls an endpoint

The conversational LLM never pays anything. The path is deterministic:

1. **`intent`** — `parseIntent(text)` classifies the turn. `x402_data_purchase`
   is chosen by the keyword table (`risk score`, `is X a rug`, `whale`,
   `smart money`, `holder`, `token price/flow/analytics`, `on-chain data`,
   `liquidity depth`, …) or, if the table misses, by one `gpt-4o-mini` call.
   `extractSubject` pulls the ticker / address into `intent.token`.
2. **`router`** — record exists + intent ∈ {`swap`, `x402_data_purchase`,
   `acp_job`} → route to `confirm`. No record → `refuse` (the deletion gate).
3. **`confirm`** — `searchCatalog(message + token)` picks the endpoint,
   `resolveX402Call` builds the concrete request, `evaluateGate` runs on the
   Sibyl-Memory caps + on-chain allowance. First-time endpoint, conservative
   risk, or amount over `WARD_AUTO_APPROVE_USD` → `interrupt()` for a yes/no on
   Telegram.
4. **`execute`** — re-reads memory and re-runs the gate on fresh values (a
   revocation or deletion in the gap still blocks here), then
   `provider.payX402({ url, method, body, expectedUsd, maxUsd })`. `x402-fetch`
   does the `402` → sign → retry-with-`X-PAYMENT` dance; the reply carries the
   data plus an `X-Payment-Response` header with the settlement tx.
5. **write-back** — `appendSpend` (idempotent on the confirmed-intent id) +
   `appendX402` (per-endpoint ok/fail → a derived endpoint-trust score).

So "the agent decides" means: the message classified as a data request, the
router saw a live authorization, and the catalog had a keyword match. It does not
proactively buy data mid-conversation — that's a separate, explicit turn.
